# 多轮会话设计：混合上下文、记忆、Skill 与 CLI

版本 v0.2 · 2026-10-02 · 状态：已实现（见第 12 节的实现状态与偏差）

本文是 `DESIGN.md` 的下一阶段。`DESIGN.md` 解决的是"一轮任务内部怎么省 token"，本文解决"面向人的多轮会话怎么既省又不丢信息"。

---

## 0. 目标、约束与非目标

**目标**：面向人的多轮编码会话。用户可以连续聊几十到几百轮，随时追问、回头、换话题、隔天继续。成本随轮数近似线性增长，而不是平方增长；质量不低于"一直带着全部上下文"的做法。

**硬约束**（来自 2026-10-02 的决定）：

1. **混合模式**：一轮任务内部只追加（吃满前缀缓存）；跨轮次按判定决定是延续还是重建。
2. **用户原话不丢**：用户自己写的每一个字，在会话内始终原样出现在上下文里，任何压缩都不能改写或删除。
3. **判定器可以用小模型**：规则先行，模糊的情况交给小模型。
4. **记忆不做图谱**：用带类型的条目加外链，图谱以后有数据证明需要时再加。
5. **基础工具要有**：读、写、编辑文件，列目录，搜索。
6. **支持 Skill + CLI**：兼容现有的 SKILL.md 格式；agent 通过 CLI 使用外部能力；`mph` 本身也要能被脚本调用。

**非目标**（这一阶段不做）：命令审批、沙箱、MCP、知识图谱、多人协作与插件生态。

**SWE 回归的定位**：只作为"不倒退"的守门测试，不作为优化目标。

## 1. 核心思路：把上下文分成"只追加的部分"和"每轮重建的部分"

两种思路之争的本质是缓存和上下文质量的取舍：

- 只追加：缓存命中高，不会漏信息；但成本随轮数平方增长，死胡同一直留在上下文里，缓存冷了以后要全价重付。
- 每轮重建：上下文有上界，内容干净；但召回漏了就是静默丢失，而且每次重建都打断缓存。

本设计的关键观察：**用户原话和每轮答复的最终形态一旦写下就不再改变，所以它们可以做成跨轮次只追加的前缀**。真正需要每轮重建的只是"本轮简报"（记忆、工作区状态），而它体积小、放在靠后的位置，重建它不会打断前面大段前缀的缓存。

于是每个请求的上下文按稳定程度从前到后排列：

```
┌──────────────────────────────────────────────────────────────┐
│ S1 静态前缀   固定提示 · 工具定义 · Skill 索引 · 项目指令        │  几乎不变，长期命中缓存
├──────────────────────────────────────────────────────────────┤
│ S2 对话记录   每轮：用户原话（原样）+ 答复卡片（定稿后不再改）   │  跨轮次只追加，命中缓存
├──────────────────────────────────────────────────────────────┤
│ S3 延续区     上一轮的工作现场（仅在判定为"延续"时携带）       │  可选
├──────────────────────────────────────────────────────────────┤
│ S4 本轮简报   常驻记忆 · 召回的记忆索引 · 工作区状态 · 预载详情 │  每轮重建，体积小
├──────────────────────────────────────────────────────────────┤
│ S5 本轮用户消息（原样）                                        │
├──────────────────────────────────────────────────────────────┤
│ S6 本轮步骤   工具调用与输出，轮内只追加，超预算批量折叠         │  轮内命中缓存
└──────────────────────────────────────────────────────────────┘
```

- **S1 + S2 是跨轮次的稳定前缀**。缓存热的时候，新一轮只需要为 S3 以后的部分付全价。
- **S4 放在 S2 之后、用户消息之前**：它每轮都变，放在后面不会打断前面的缓存；离用户消息近，模型的注意力也更集中。
- **S6 沿用现有的轮内机制**：输出整形、批量折叠带滞回、recall。

"延续还是重建"由判定器决定，差别只在 S3：延续时把上一轮的工作现场（最后若干步的工具调用与输出）原样带上；重建时 S3 为空，只靠 S4 的简报。无论哪种，S2 都完整存在，所以用户原话永远都在。

## 2. 对话记录（S2）与用户原话保真

### 2.1 记录存储

每个会话有一份只追加的对话记录：`~/.mph/harness/transcripts/<sid>.jsonl`。每一轮写两条：

```jsonc
{"kind":"user","turn":12,"at":"2026-10-02T10:03:11Z","text":"<用户原文，逐字>","sha1":"…","attachments":[]}
{"kind":"answer","turn":12,"at":"…","full_artifact":"a1b2c3…","card":"<答复卡片>","files_changed":["src/x.ts"],"status":"done"}
```

- **用户消息在任何处理之前先落盘**。即使后续的模型调用失败或进程崩溃，原话也已经保存。
- 记录只追加，不修改。历史的唯一来源是这个文件，S2 每次都由它确定性地渲染出来。

### 2.2 用户原话保真规则

1. **用户自己写的文字永不改写、永不删除、永不摘要**。会话内每一轮的用户文字都原样出现在 S2 里。
2. **大块粘贴内容可以外置，但只在满足条件时**。条件：单块超过 `paste_externalize_tokens`（默认 2000），是代码块、日志或堆栈这类可识别的粘贴内容，而且已经过去 `paste_keep_turns` 轮（默认 2 轮）。外置后原位置保留一行占位：
   `[粘贴内容 · 日志 · 412 行 / 5.1K tok · 头 3 行 … 尾 3 行 · recall("p9f2…")]`
   粘贴所在的那一轮，以及之后的 2 轮里，粘贴内容都原样出现。
3. **区分用户文字和粘贴内容**：用 Markdown 代码围栏、连续多行的日志特征、堆栈特征来识别。识别不确定时，按用户文字处理，即不外置。宁可多花 token，不可错删原话。
4. **自动校验**：每次组装请求时，断言当前会话所有用户消息的文字部分都逐字出现在请求里。这条断言同时写进单元测试和账本（`user_fidelity: ok|violated`），dashboard 上出现一次 violated 就算严重缺陷。

**为什么"全部原样保留"在成本上可以接受**：用户消息通常很短。按每条约 150 token 计，200 轮约 30K token，而且处在只追加的前缀里，缓存热的时候按十分之一计价。真正大的是粘贴内容，规则 2 已经处理了这部分。

**极端情况**：如果用户文字本身超过 `user_text_budget`（默认 60K），不删除任何内容，而是在 dashboard 上提示"会话过长，建议 /fork 或开新会话并带上记忆"。是否继续由用户决定。

### 2.3 答复卡片

助手的完整答复存进 artifact，S2 里放的是定稿后的"答复卡片"：

- **最近 `answer_verbatim_turns` 轮（默认 3 轮）的答复原样放入**。
- 更早的答复替换为卡片，约 120 token 以内，内容包括：结论、改动的文件、验证了什么、遗留问题，以及 `recall(id)`。
- **卡片在该轮结束时一次性生成，之后不再改变**。为了让"最近 3 轮原样，更早的用卡片"不至于每轮都改动前缀，S2 按"纪元"渲染：每 `answer_verbatim_turns` 轮把一批原样答复一次性换成卡片。这样每 3 轮才打断一次 S2 的缓存，而不是每轮都打断。
- 卡片优先由规则从答复中抽取（答复本来就要求"先写结论、列出改动文件"）。抽取失败时才调用小模型。

## 3. 每轮的生命周期

```
用户输入
  │ ① 原话落盘（transcript.jsonl）
  ▼
② 判定 + 召回（一次小模型调用，带规则兜底）
  │   输出：延续 / 重建；要放进索引的记忆；需要预载详情的记忆；需要预载的 skill
  ▼
③ 组装上下文 S1…S5（确定性，带用户原话保真断言）
  ▼
④ 执行本轮步骤 S6（主模型；工具：读写编辑、搜索、run/wait、recall、记忆、skill）
  ▼
⑤ 回合收尾
      · 生成答复卡片，写入 transcript
      · 抽取记忆（规则 + 小模型），去重合并后写入记忆库
      · 记录账本：token、缓存、判定结果、召回命中或遗漏
```

### 3.1 判定器（gate）

**输入特征**（全部可以离线计算，不需要模型）：

| 特征 | 说明 |
|---|---|
| `idle_s` | 距上一轮结束的时间，与 `cache_ttl_estimate_s` 比较判断缓存冷热 |
| `topic_sim` | 新消息与上一轮用户消息及其答复卡片的词法相似度 |
| `back_ref` | 是否出现指代：刚才、上面、那个、继续、再、also、that、it… |
| `explicit` | 用户命令：`/continue`、`/new`、`/fork` |
| `S3_size` | 上一轮工作现场的 token 数 |
| `files_overlap` | 新消息提到的文件与上一轮改动文件的交集 |

**规则**（按顺序，先命中先生效）：

1. 用户显式命令优先。
2. 缓存已冷（`idle_s > ttl`）→ **重建**。此时延续也要全价付费，没有理由携带 S3。
3. `back_ref` 为真，或者 `files_overlap` 非空，并且缓存热 → **延续**。
4. `topic_sim` 低于下阈值，并且没有指代 → **重建**。
5. 其余是模糊区，交给小模型。

**小模型调用**：判定和记忆召回合并成一次调用，省一次往返的延迟。输入是新消息、最近 2 轮的用户原话和答复卡片、最多 40 条记忆候选的标题、最多 20 个 skill 的名称和描述。输出严格的 JSON：

```json
{"action":"continue|rebuild","why":"…","memory_ids":["m12","m40"],"detail_ids":["m12"],"skills":["clickhouse-query"]}
```

小模型超时或输出无法解析时，退回规则结果：模糊区按"延续"处理（保守，不丢信息），记忆取打分排名前 K 条。

**延续时的 S3 上限**：最多携带上一轮最后 `window` 条观察，并且不超过 `continue_budget`（默认 20K）。超出部分按现有折叠规则变成存根。

### 3.2 成本账

设：S1+S2 为稳定前缀 P，S3 为上一轮现场 W，S4 为简报 B，本轮步骤数为 k，缓存价格系数为 0.1。

- **延续、缓存热**：每步付 0.1·(P+W+B+…) 加上新增部分。W 只在第一步按全价付一次，之后都命中缓存。
- **重建、缓存热**：P 仍然命中缓存，省掉了 W 带来的全部成本，代价是模型可能多读几次文件。
- **缓存冷**：无论哪种做法 P 都要全价重付一次。此时重建明显更划算，因为至少省掉了 W。

结论：**判定器的价值主要在缓存热且话题相近的情况**，其他情况规则就能给出答案。这也是小模型只处理模糊区的原因。

## 4. 记忆

### 4.1 记什么、不记什么

**记忆要存仓库里没有的东西**：

| 类型 `type` | 内容 | 例子 |
|---|---|---|
| `goal` | 会话或项目的目标 | 把压缩逻辑做成可插拔的步骤 |
| `constraint` | 用户给出的限制 | 不要改公共 API；测试用 py39pd 环境 |
| `preference` | 用户的习惯和偏好 | 回答用中文；先给结论 |
| `decision` | 做过的决定及原因 | 记忆库用 node:sqlite，不引入依赖，因为… |
| `fact` | 关于代码的事实，必须带文件链接 | `rewrite()` 的折叠边界按 call_id 单调前进 |
| `attempt` | 试过但失败的路，以及原因 | 每步都折叠会让成本当量变差，因为… |
| `open` | 未决问题、待办 | 判分器对含空格的测试 ID 处理有误 |
| `procedure` | 做某件事的步骤 | 怎么跑 R6 回归 |

**不记的东西**：可以直接从代码读到的内容（函数签名、文件结构），能从 git 查到的历史，一次性的中间结果。代码事实只记"不读很多代码就看不出来的结论"，并且必须带上文件链接，以便判断它是否过期。

### 4.2 数据模型

```ts
interface MemoryEntry {
  id: string;                    // "m" + 序号，短，便于模型引用
  type: "goal" | "constraint" | "preference" | "decision" | "fact" | "attempt" | "open" | "procedure";
  scope: "session" | "project" | "user";   // project 以 git 根目录为键
  title: string;                 // 一行，≤ 80 字符，召回索引里只显示它
  body: string;                  // ≤ 300 token，详情
  links: { kind: "file" | "turn" | "artifact" | "commit" | "skill" | "url"; ref: string; hash?: string }[];
  source: { session: string; turn: number; by: "user" | "model" | "rule" };
  quote?: string;                // 来源于用户原话时，逐字引用原句
  status: "active" | "superseded" | "stale" | "done";
  supersedes?: string;           // 被它取代的旧条目
  pinned: boolean;               // 常驻层
  created: string; updated: string; last_used?: string; use_count: number;
}
```

- **`quote` 字段**：凡是来自用户的约束和偏好，都逐字保存用户原句。模型看到的是"用户原话"而不是改写后的版本，这是第 2 节保真原则在记忆里的延伸。
- **`links[].hash`**：`fact` 指向的文件区域内容哈希。召回时重新计算，不一致就标为 `stale` 并提示"文件已变化，请重新读取"。

### 4.3 存储

- **SQLite**，使用 Node 24 自带的 `node:sqlite`，不新增依赖。库文件为 `~/.mph/memory.db`。
- **全文索引**：FTS5，`tokenize='trigram'`，中英文都能检索，已验证可用。trigram 要求查询至少 3 个字符，更短的查询退回 `LIKE` 匹配。
- **导出**：`mph memory export` 输出 JSONL，便于查看、编辑和备份。`mph memory import` 导回。
- **不做向量检索**。第一版只用 BM25 加规则打分。等多轮评测显示召回率不够时，再加 embedding 作为候选来源之一，接口预留好。

### 4.4 三层注入

| 层 | 内容 | 位置 | 预算 |
|---|---|---|---|
| L0 常驻 | `pinned` 条目：当前会话的目标、项目和用户的约束与偏好、仍然有效的关键决定 | S4 顶部 | ≤ 800 token |
| L1 索引 | 本轮召回的条目，每条一行 `[m12 decision] 记忆库用 node:sqlite…` | S4 | ≤ 12 条，≤ 600 token |
| L2 详情 | 条目的 body 和链接 | 预载最多 2 条放进 S4；其余由模型调用 `memory_get` 获取 | 每条 ≤ 300 token |

L1 末尾始终附一行：`记忆库中还有 N 条相关性较低的条目，可用 memory_search(query) 查找`。模型知道"还有别的"，召回漏掉某条时可以自己去找，这是防止静默丢失的安全阀。

**pinned 的来源**：用户显式说"记住…"或者给出约束时由规则直接 pin；`goal` 和 `constraint` 类型默认 pin；用户可以 `/memory pin|unpin <id>`。L0 超预算时，按 `scope` 优先级（session > project > user）和 `last_used` 排序截断，被截断的降级到 L1 候选。

### 4.5 召回

1. **候选生成**（无模型，几毫秒）：
   - FTS5 BM25：查询词来自新消息加上最近 1 轮的用户原话。
   - 链接重叠：新消息提到的文件、上一轮改动的文件，与条目 `links` 的交集。
   - 类型先验：`constraint`、`attempt` 加权。避免重蹈覆辙比回忆事实更重要。
   - 时间衰减：按 `last_used` 和 `updated`，仅用于排序，从不删除。
   - 取前 40 条作为候选。
2. **小模型重排**：与判定器合并为同一次调用（见 3.1），选出 ≤ 12 条进 L1、≤ 2 条预载详情。
3. **兜底**：小模型失败时，按打分取前 8 条。
4. **使用反馈**：模型调用了 `memory_get(id)`、答复里引用了 `m12` → `use_count++` 并更新 `last_used`。模型通过 `memory_search` 找到了一条不在 L1 里的条目并实际使用 → 记一次**召回遗漏**，写进账本，sidecar 用它来调候选数量和类型权重。

### 4.6 写入

三条写入路径：

1. **规则写入**（每轮收尾，确定性）：
   - 用户原话里的显式指令：匹配"记住""以后都""不要""必须""always""never"等句式 → `constraint` 或 `preference`，`quote` 保存原句，pin。
   - 工作区事实：改动过的文件、最后一次测试状态，写入 session 范围的 `fact`，这部分取代现有的状态摘要。
2. **主模型写入**：新工具 `remember(type, title, body, links)`，取代现有的 `state_update`。区别在于 `state_update` 每次覆盖整段笔记，`remember` 是追加带类型的条目。固定提示要求模型在做出决定、放弃某条路、确认某个代码事实时调用它。
3. **小模型抽取**（每轮收尾，可关闭）：输入本轮的用户原话、答复全文、工具调用列表，输出至多 5 条候选条目，严格 JSON。这一路负责捕捉主模型忘记记录的决定和失败尝试。

**去重合并**：写入前，用标题做 FTS 检索同类型、链接有重叠的已有条目：

- 没有相似条目 → 新建。
- 有相似条目且内容一致 → 跳过，`use_count++`。
- 有相似条目但内容有变化 → 小模型判断"更新"还是"取代"。取代时旧条目标为 `superseded`，新条目记录 `supersedes`。

**作用域提升**：session 范围的 `decision`、`fact`、`procedure` 在会话结束时由小模型判断是否值得提升为 project 范围。用户的 `preference` 默认就是 user 范围。

**过期与清理**：不自动删除。`fact` 在链接文件变化后标为 `stale`；`open` 被解决后标为 `done`；`mph memory gc` 列出长期未用的条目供人工确认。

### 4.7 跨会话

新会话开始时 S2 为空，L0 和 L1 来自 project 和 user 范围的记忆。这就是"每个会话从新开始、靠记忆接上"的路径。用户也可以 `mph chat --resume <sid>` 延续旧会话，S2 完整恢复。

## 5. Skill 与 CLI

### 5.1 Skill

**格式**：兼容现有 Agent Skills 约定。一个目录包含 `SKILL.md`，开头是 `name` 和 `description` 的 frontmatter，可选 `scripts/`、`references/` 等子目录。本机 `~/.codex/skills`、`~/.claude/skills` 里已有的 skill 无需修改即可使用。

**发现路径**（同名时前者优先）：

1. 项目内：`.agents/skills/`、`.claude/skills/`、`.codex/skills/`
2. 用户级：`~/.mph/skills/`、`~/.agents/skills/`、`~/.claude/skills/`、`~/.codex/skills/`

**渐进加载**，和记忆的三层是同一个思路：

| 层 | 内容 | 位置 |
|---|---|---|
| 索引 | 每个 skill 一行：名称 + 截断到 200 字符的描述 | S1 静态前缀，长期命中缓存 |
| 正文 | `SKILL.md` 全文 | 模型调用 `skill(name)` 时以工具输出的形式进入 S6；判定器认为强相关时预载到 S4 |
| 附属文件 | 参考资料、脚本 | 模型按正文的指引用 `read` 读取、用 `run` 执行 |

- **skill 正文在本轮内不折叠**，标记为 `pinned_observation`，避免模型做到一半丢掉操作说明。轮次结束后按普通输出折叠，可以 recall。
- **依赖检查**：frontmatter 可以声明 `requires: [gh, jq]`。启动时检查这些 CLI 是否在 PATH 上，缺失的 skill 在索引里标注"不可用：缺少 gh"。
- **skill 数量很多时**：索引超过 `skill_index_budget`（默认 1500 token）后，S1 只放 skill 的数量和最常用的若干个，其余由判定器按本轮相关性挑选放进 S4。

**与记忆的关系**：`procedure` 类记忆被反复使用、步骤稳定之后，可以用 `mph skill promote m40` 生成一个 skill 草稿。这是"临时经验"沉淀为"可复用能力"的路径。

### 5.2 CLI：agent 通过命令行使用外部能力

不做 MCP，外部能力一律以 CLI 的形式提供：agent 用 `run` 调用，skill 负责告诉它怎么用。这样做的好处是工具定义不占 S1 的空间，能力的增减不会改变静态前缀，也就不会打断缓存。

为了让 CLI 调用省 token、结果可靠：

- **输出整形器按 CLI 注册**：现有的 pytest、rg、日志整形器之外，加上 `gh`、`git`、`kubectl`、`jq` 等常见 CLI 的整形规则，也允许 skill 用 frontmatter 声明自己脚本的输出整形规则。
- **结构化优先**：固定提示和 skill 引导模型优先使用 `--json`、`--format`、`-q` 这类参数，配合 `jq` 只取需要的字段。
- **长时间运行的命令**：继续使用 `run(background=true)` 加 `wait`，不做轮询。

### 5.3 CLI：`mph` 本身可被脚本和其他 agent 调用

| 能力 | 形式 |
|---|---|
| 非交互单轮 | `mph run "…"`、`mph run --prompt-file f`、`echo "…" \| mph run -` |
| 续接会话 | `mph run --session <sid> "…"`；`mph run --resume-last "…"` |
| 机器可读输出 | `--json`：每行一个事件（step、tool、text、usage、final），最后一行为结果对象 |
| 退出码 | 0 完成；2 达到步数上限；3 模型错误；4 用户原话保真断言失败 |
| 记忆与 skill 管理 | `mph memory list\|search\|get\|pin\|export\|import\|gc`；`mph skill list\|show\|promote` |

## 8. 评测：多轮金标集

SWE 只守"不倒退"。多轮能力需要单独的评测，这是整个方案能否迭代的前提，所以排在实现之前。

### 8.1 用例形式

每个用例是一个脚本化的对话，用户消息固定，不用模型扮演用户，以保证可复现。每一轮可以带检查点：

```yaml
id: constraint-persists
repo: fixtures/mini_calc          # 小型夹具仓库，评测时复制一份
turns:
  - user: "给 calc.py 加一个 divide 函数。注意：不要修改 add 和 sub 的签名。"
  - user: "再加一个 power。"
  - user: "把 add 改成支持任意多个参数。"     # 与第 1 轮的约束冲突
    check:
      - judge: "答复是否指出这与第 1 轮'不要修改 add 签名'的约束冲突，并询问或给出不破坏签名的方案"
      - cmd: "python -c 'import inspect,calc; assert list(inspect.signature(calc.add).parameters)==[\"a\",\"b\"]'"
```

检查方式有三种：`cmd`（命令退出码）、`contains`（答复包含某些文字）、`judge`（用强模型按评分标准判定，三次取多数）。

### 8.2 用例类别（第一版约 30 个）

| 类别 | 考察点 |
|---|---|
| 指代 | "刚才那个函数""上面第二个方案""回到之前那个 bug" |
| 约束保持 | 早期约束在 10 轮以后仍然生效 |
| 偏好 | 输出语言、格式、测试命令等偏好跨轮次、跨会话生效 |
| 换题与回题 | 中途切到无关话题，再回到原话题继续 |
| 长粘贴 | 粘贴大段日志，几轮之后追问日志里的细节，检验外置与 recall |
| 失败经验 | 试过的方案失败后，后续不再重复同样的尝试 |
| 跨会话 | 新会话里问"上次我们决定用什么存储" |
| 原话引用 | "我第一句话让你做什么？"必须逐字复述 |
| Skill | 需要按某个 skill 的步骤完成的任务 |

### 8.3 指标

| 指标 | 说明 |
|---|---|
| 检查点通过率 | 主质量指标 |
| 用户原话保真 | 每个请求的断言结果，必须 100% |
| 每轮 token、缓存命中率、成本当量 | 主成本指标 |
| 召回遗漏率 | 模型通过 `memory_search` 补回的条目占实际用到条目的比例 |
| 判定器分布 | 延续与重建的比例、小模型调用比例、判定耗时 |

### 8.4 对照组

| 组 | 做法 |
|---|---|
| `full` | 什么都不压缩，一直追加，相当于"带全部上下文" |
| `proxy` | 现有 mph-proxy 的做法：大上下文追加加折叠 |
| `hybrid` | 本设计 |
| `hybrid-norules` | 本设计但判定器总是重建，用于衡量判定器的价值 |

**验收标准**：`hybrid` 的检查点通过率不低于 `full` 减 2 个百分点；用户原话保真 100%；20 轮以上的用例中，成本当量不高于 `full` 的一半。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 召回漏掉关键记忆，模型静默做错 | L1 末尾提示还有更多条目；`memory_search` 兜底；`constraint` 和 `attempt` 加权；召回遗漏率进账本，sidecar 据此调参 |
| 记忆写入质量差，垃圾进垃圾出 | 每条必须有类型和来源；用户约束保存原句；去重合并；`mph memory list` 和导出便于人工检查；评测覆盖 |
| 记忆与代码不一致 | `fact` 绑定文件哈希，变化即标 `stale` |
| 小模型判定增加延迟 | 规则先行，只有模糊区才调用；判定与召回合并为一次调用；设置超时，超时走兜底 |
| S2 越来越长 | 用户文字本身很小；答复按纪元换成卡片；粘贴内容外置；超过阈值只提示，由用户决定 fork 或新开 |
| 纪元切换打断缓存 | 每 `answer_verbatim_turns` 轮才切换一次；sidecar 观察切换后的缓存恢复情况来调纪元长度 |
| 不同模型对布局的敏感度不同 | 布局由 `assemble.ts` 统一产出，可以按模型做 profile；多轮评测按模型分别跑 |
